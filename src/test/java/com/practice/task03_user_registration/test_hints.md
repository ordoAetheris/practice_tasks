# Подсказки для тестирования: UserRegistrationService

## Обязательно протестировать
- Успешная регистрация — пользователь создан с корректными полями
- Регистрация с пустым логином — IllegalArgumentException
- Регистрация с невалидным email (без @, без домена) — IllegalArgumentException
- Регистрация с дублирующимся логином — IllegalStateException
- Регистрация с дублирующимся email — IllegalStateException
- Поиск по логину — существующий и несуществующий
- Поиск по email — существующий и несуществующий
- Удаление существующего пользователя
- Удаление несуществующего пользователя — false
- Сортировка по дате регистрации

## Продвинутые кейсы
- Регистрация после удаления — логин и email снова доступны
- Email с разным регистром — считаются одинаковыми или нет?
- Логин с пробелами
- Автоинкремент id — корректная генерация
- Пустой список пользователей — getAllSortedByRegistrationDate возвращает пустой список

## Веер вариантов (b–e) — per-variant подсказки

### B — гонка уникальности (UserRegistrationServiceB)
- Стресс: пул M потоков (CountDownLatch на старт) регистрируют ОДИН email → ровно 1 успех, M-1 × IllegalStateException; итоговый размер хранилища == 1.
- То же на одинаковый login.
- Повторить прогон много раз (флаки-гонки ловятся не с первого раза) — например, 100 итераций стресса.
- Проверить, что при РАЗНЫХ login+email параллельная регистрация не блокирует друг друга без нужды (не один глобальный лок на весь мир — по вкусу, но замерить).

### C — двухключевой atomic reserve (UserRegistrationServiceC)
- login свободен, email занят → отказ, и login ПОСЛЕ отказа снова свободен (нет «утёкшего» резерва).
- Симметрично: email свободен, login занят → откат, email свободен.
- Гонка: поток1 берёт (loginA, emailX), поток2 — (loginB, emailX) одновременно → один успех, второй откатывает свой login.
- После успешной регистрации оба индекса указывают на одного и того же пользователя (консистентность).

### D — идемпотентный повтор (UserRegistrationServiceD)
- Дважды register с ОДНИМ requestId → один и тот же User (по id), размер хранилища == 1.
- Гонка: два потока, один requestId → ровно один User, оба вызова его возвращают.
- Новый requestId, но занятый login/email → IllegalStateException (это НЕ идемпотентный повтор).
- Разные requestId с разными данными → два разных пользователя.

### E — edge/валидация/нормализация (UserRegistrationServiceE)
- Таблица грязных входов: null login, "", "   ", null email, "no-at", "a@", "@x", "a@x" (ок).
- "A@X.com" и "a@x.com" — ОДИН email (нормализация lower+trim до проверки уникальности).
- login с пробелами по краям — trim; зафиксировать правило регистра login и проверить его.
- После delete — нормализованные login/email снова доступны.
- id без дыр после нескольких register/delete.
