# Подсказки: контракты value-объекта Person (task101)

## Обязательно протестировать
- equals: два Person с одинаковыми значимыми полями равны; с разными — нет.
- equals null → false; equals объекта другого класса → false; рефлексивность/симметричность.
- hashCode: equal объекты дают равный hashCode. Положить 2 «одинаковых» в HashSet → size == 1.
- Как ключ HashMap: put по одному Person, get по «равному» другому экземпляру → находит значение.
- compareTo: сортировка по (lastName, firstName, birthYear); TreeSet не теряет и не дублирует.
- Согласованность: compareTo == 0 тогда и только тогда, когда equals == true.
- Неизменяемость: изменить список, переданный в конструктор ПОСЛЕ создания → объект не меняется.
- Геттер emails: попытка мутировать возвращённый список не меняет объект (UnsupportedOperation или копия).

## Классические баги (не допустить + уметь объяснить)
- `hashCode()` возвращает константу (1) — «работает», но всё в один бакет, O(n).
- equals есть, hashCode нет (или наоборот) — рассинхрон, HashSet двоит объекты.
- equals через `==` для строк вместо `.equals`.
- compareTo не согласован с equals → TreeSet «теряет» элементы.
- Нет defensive copy → внешний код мутирует внутренний список (нарушение immutability).
- equals по `getClass()` vs `instanceof` — знать разницу (наследование/симметричность).
- Сериализация без `serialVersionUID` → InvalidClassException при эволюции класса.
